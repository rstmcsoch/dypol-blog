==================================================
3. CONFIRMED DESIGN DIRECTION
==================================================

The website MUST use a:

NEOBRUTALISM AESTHETIC

The primary visual foundation is:

BLACK + WHITE

Black and white should dominate the overall website.

The design should feel like a sophisticated, modern neobrutalist publication rather than chaotic experimental brutalism.

Use strong visual hierarchy, deliberate geometry, clear borders, confident typography, hard/offset depth where appropriate, and strong interaction states.

The website must remain highly usable and readable.

==================================================
4. GRAIN / TEXTURE DIRECTION
==================================================

The design should include a subtle grain/noise treatment in selected COLORED areas.

Important:

- White areas should generally remain clean.
- Black areas should generally remain clean.
- Colored accent areas may contain subtle grain.
- Grain must never reduce text readability.
- Grain must never become a continuously animated visual effect.
- Do not use huge texture images when a small reusable implementation can achieve the effect.
- Prefer lightweight CSS/pseudo-element or tiny optimized texture techniques.
- Avoid canvas/WebGL for grain.
- Avoid expensive real-time noise generation.
- Grain should look intentional, refined and editorial.
- Grain should add character without making the website feel dirty or low quality.

The visual relationship should be:

BLACK + WHITE = structural identity
COLOUR + GRAIN = selective visual emphasis

Colored areas must not take over the website.

==================================================
9. RESPONSIVENESS
==================================================

Responsiveness is a PRIMARY REQUIREMENT, not a final polish task.

The website must work correctly across:

- very small phones
- normal phones
- large phones
- small tablets
- large tablets
- portrait tablets
- landscape tablets
- laptops
- desktop monitors
- ultrawide monitors
- very large screens

Do not design only around common desktop widths.

The UI must respond to actual available space rather than relying solely on rigid device-specific assumptions.

Use:

- fluid containers
- flexible grids
- fluid typography
- responsive image sizing
- responsive gaps
- wrapping navigation where appropriate
- container-aware layouts where beneficial
- robust media aspect ratios

Test both portrait and landscape orientations.

There must be:
- no accidental horizontal scrolling
- no clipped text
- no overlapping cards
- no broken navigation
- no impossible button layouts
- no distorted images
- no unreadable article content

==================================================
10. DEVICE-AWARE BEHAVIOR
==================================================

Where technically appropriate, respect browser/device capabilities and settings such as:

- reduced motion
- pointer capabilities
- hover availability
- viewport dimensions
- orientation
- forced-colors/accessibility environments
- available screen space

Do not render expensive effects simply because the device technically supports them.

The goal is graceful degradation.

A low-end phone should receive the essential website experience without paying for effects it does not need.

==================================================
11. PERFORMANCE
==================================================

Performance is one of the most important requirements.

The website should feel extremely fast even on basic devices and slower networks.

Prioritize:

- server-first rendering where practical
- minimal client-side JavaScript
- React Server Components where appropriate within the existing stack
- progressively enhanced interactions
- minimal dependencies
- small JavaScript bundles
- small CSS output
- optimized images
- appropriate image dimensions
- lazy loading below-the-fold images
- priority loading only for genuinely critical media
- prevention of layout shift
- fixed media aspect ratios where useful
- no unnecessary hydration
- no unnecessary re-renders
- no expensive global state for simple UI
- no giant client-side content payloads
- no decorative WebGL
- no continuously animated backgrounds
- no unnecessary animation libraries
- no large third-party widgets
- no auto-playing video unless explicitly required later
- no rendering of hidden components that are not needed

Do not sacrifice performance just to create visual effects.

The page should still look distinctive when expensive effects are disabled.

==================================================
12. GRAIN PERFORMANCE
==================================================

The grain implementation must be especially lightweight.

Do not:
- render animated noise every frame
- use large full-page raster textures
- use WebGL
- repeatedly generate random pixels with JavaScript

Prefer:
- CSS pseudo-elements
- tiny compressed texture assets if actually necessary
- cached static texture
- opacity/blur/compositing kept under control

Use the same reusable mechanism across colored areas instead of loading separate large assets for every card.

==================================================
13. IMAGE / MEDIA PERFORMANCE
==================================================

Use the existing image optimization capability in the repository where applicable.

Media must:

- preserve aspect ratio
- avoid distortion
- load responsively
- use appropriate dimensions
- lazy-load when not critical
- avoid oversized originals being sent to small devices
- reserve layout space before loading where possible
- support accessible alternative text

Use the existing R2 infrastructure for future uploaded blog media.

Existing bucket:
`dypol-blog-media`

Do not introduce another media-storage service.

14. PUBLIC CONTENT ARCHITECTURE
==================================================

The public website must be designed around structured content rather than hard-coded page markup.

The architecture should clearly separate:

- site configuration
- navigation configuration
- content
- article metadata
- article body
- media
- categories
- tags
- publication state
- SEO metadata

Do not hard-code information that will clearly need to be changed by an administrator later.

The visual layer should consume structured content.

==================================================
15. AUTOMATION-FIRST ARCHITECTURE
==================================================

A very large portion of future articles will be produced through an automated content workflow.

Therefore the entire content system MUST be AI-agent/provider agnostic.

Do not hard-code the architecture around any specific AI company, model, bot or provider.

The system should allow the automation provider/agent to be replaced later without redesigning the website or rewriting the content model.

The future automated workflow should be able to work through stable structured interfaces rather than depending on fragile visual UI automation.

The system should make it easy for an automated agent to:

- create an article
- update an article
- save a draft
- add/update metadata
- assign categories
- assign tags
- attach/select media
- update SEO metadata
- publish
- unpublish
- schedule where later supported
- correct/retry failed submissions

Do not require unnecessary human clicks for automated operations.

==================================================
16. AUTOMATION RELIABILITY
==================================================

Design the underlying content interfaces to minimize automation failures.

Prefer:

- deterministic structured payloads
- schema validation
- predictable field names
- explicit success/error responses
- idempotent operations where appropriate
- retry-safe operations
- clear publication states
- stable identifiers
- validation before publishing
- media references instead of fragile UI selections
- server-side authorization
- transactional behavior where applicable
- clear failure reporting
- no dependence on screen coordinates or DOM scraping

An automation agent should NOT have to pretend to be a human user clicking through multiple pages just to publish an article.

The system should provide an efficient machine-readable path while still supporting a complete human interface.

==================================================

==================================================

Never make performance depend on the user owning a powerful device.
