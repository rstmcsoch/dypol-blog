### How each half works today

**Public site.** `__root.tsx` loads `getShell()` → `readShell()` → `publicCatalog()`. If D1 throws,
`publicCatalog()` falls back to the built-in `staticCatalog()` (seed articles from
`src/content/articles.ts`) so pages never error. `readShell()` returns `{ site, trending }` where
`trending` comes from `tickerEntries(site.trending, publishedArticles)`. The homepage is
`src/routes/index.tsx`: four **hard-coded** section renderers (`featured`, `also`, `latest`,
`topics`) switched on/off and ordered by `site.home.sections`. The article sidebar is
`src/components/site/article-view.tsx`: four fixed block names (`tags`, `related`, `newStories`,
`share`) with one shared `count`.

**Automation.** The site is a *pull* target: an external AI app (Claude/ChatGPT/Grok/CLI) holds
the token, decides the schedule, researches, writes and calls the MCP tools. `submit_article_draft`
validates and stores a draft through the same `saveArticle()` the desk uses; quality flags
(`src/lib/automation/policy.ts`) always keep flagged pieces as drafts; `publish_article_if_allowed`
publishes only when *every* policy rule passes. `src/lib/automation/provider.ts` contains request
builders/parsers for xAI, OpenAI, Anthropic, Gemini, OpenRouter and any OpenAI-compatible base URL —
but **nothing ever calls them** ("nothing schedules or triggers a run, so no request is ever made").

### Production verification (read-only, over the network)

* `https://dypolblog.rstmcsoch.workers.dev/` renders; the ticker strip **is present** with label
  "Now" and 3 article links.
* `GET /mcp` → `401 Unauthorized` (not the 503 "endpoint disabled" path) ⇒ **`MCP_TOKEN` is set in

## 2. Confirmed bugs (root cause → impact)

### B1 — Automation configuration is global, not per-automation *(verified)*
`src/content/automation.server.ts:11` reads one row (`site_settings.id = 'automation'`), and
`saveAutomationSettings` overwrites that whole row. `src/routes/admin/automation.tsx` posts the
entire record. **Impact:** two automations cannot coexist — the second save silently overwrites the
first provider, schedule, topics, policy and publishing mode. This blocks the whole Phase 3 goal.

### B2 — "Schedules" exist only inside the external AI app *(verified)*
There is no `triggers.crons` in `wrangler.jsonc`, no `scheduled` export anywhere, no `next_run_at`
state. `docs/ADMIN-GUIDE.md` even states the schedule is set in the AI app. **Impact:** nothing in
the product can run on a schedule; "schedules survive deployments" is unsatisfiable; a paused/lost
external task silently stops publishing with no in-app signal.

### B3 — The ticker is a hidden-scrollbar horizontal scroller, not a rotating ticker *(verified)*
`src/components/site/trending-bar.tsx` renders **all** items at once; `styles.css:596` gives
`.trend__list` `overflow-x: auto` + `white-space: nowrap` and hides the scrollbar
(`.trend__list::-webkit-scrollbar { display: none }`). With `animate: false` (the code default) the
row simply overflows. **Impact:** on phones (and any narrow viewport) the strip looks empty or
truncated mid-word and there is no affordance that it scrolls — the reported "the ticker
disappeared". Root cause is the rendering model, not a lost data source.

### B4 — Pinned ticker entries vanish silently *(verified)*
`tickerEntries()` (`src/content/ticker.ts:14-18`) maps pinned slugs over **published** articles and
drops anything not found. So unpublishing an article removes it from the ticker with no message;
if every pinned slug is unpublished the entire bar disappears. Compounding it,
`saveSettings()` (`repository.server.ts:642`) *silently rewrites the saved config*
(`next.trending.slugs = next.trending.slugs.filter(...)`) so the admin's selection is destroyed the
next time any settings page is saved. A control that appears to work but silently changes data.

### B5 — Ticker cannot be controlled beyond label/source/count/animate/speed *(verified)*
No rotation interval, no per-source category filter, no manual ordering, no preview, and the
"Latest/Newest" source cannot be limited to a category. `source: "pinned"` has no order control
(`slugs` order is used, but the desk renders plain checkboxes).

### B6 — Publish race can record a publish that did not happen *(verified)*
`src/lib/mcp/tools.server.ts:355-359`: the `update … where id = ? and status = 'draft'` result is
never inspected, yet `recordRun({ tool: "publish_article_if_allowed", outcome: "published" })` runs
unconditionally. `automatedPublishesToday()` counts **those log rows**, so a second concurrent call
for the same article both reports `published: true` and inflates the daily cap, which then blocks
legitimate publishes. **Impact:** misleading run status + wrongly exhausted daily limit.

### B7 — Run outcomes can be lost silently *(verified)*
`recordRun()` swallows every error (`automation.server.ts:45`) and returns `null`; callers log
nothing. `submit_article_draft` then still answers `ok: true, drafted`. **Impact:** history gaps
without any warning — the admin sees "no runs" instead of "logging failed".

### B8 — Desk has no theme support and hard-codes light colours *(verified)*
`styles.css:1369-1440` fixes `color-scheme: light` and literal colours (`#f6f7f9`, `#ffffff`,
`#fafbfc`, `#1d2330`, `#eef0f3`, `#bcd0ff`, `#f0c4c4`, `#b7e0c7`, `#0f172a`,
`rgba(246,247,249,.95)`, `.adm-dialog { background: #fff }`). There is no theme selector, no
persistence, no `prefers-color-scheme` handling for the desk.

### B9 — Homepage / sidebar are not editable beyond 4 fixed toggles *(verified)*
Homepage sections are a closed union (`HOME_SECTION_IDS`, `validate.ts:64`) with fixed renderers
keyed by id; the sidebar is a closed union (`SIDEBAR_BLOCKS`) with one shared count. There is no add,
remove, duplicate, per-block settings, block library, ordering beyond the four fixed items, draft /
publish separation, or preview.

### B10 — Naming/configuration mismatch around `dypol-blog` vs `dypolblog` *(verified)*
`wrangler.jsonc` is correct (`name: "dypolblog"`, matching the live hostname), but
`cloudflare.config.ts` (dead `vinext`/Next.js config) declares the Worker **`dypol-blog`** plus a
`dypol-blog-response-store` service, and `src/lib/mcp/protocol.ts` / `http.server.ts` announce
`dypol-blog` in MCP server info and the `WWW-Authenticate` realm. Leftover Next.js artifacts
(`app/`, `next.config.ts`, `vercel.json`, the Next.js `README.md`) describe a stack the project no
longer deploys. **Impact:** confusing/incorrect deployment surface; a future operator can deploy or
debug the wrong Worker name.

* `src/lib/automation/policy.ts` (`draftFlags`, `publishDecision`, `sourceProblems`) and

* `src/lib/auth/*`, `src/lib/write-guard.server.ts`, `src/lib/write-policy.ts` — authorization and

* `scripts/e2e/*`, `npm run test:src|test:scripts` — the existing test harness.

## 6. Prioritised plan (the order actually implemented)

1. **Schema** — additive migration: `automations`, `automation_schedule`, `automation_runs` extra
   columns, `article_views` (a genuine, privacy-safe popularity metric), indexes. No destructive
   change; the legacy `site_settings.automation` row is migrated on read.
2. **Automation core** — per-automation settings model, exact-match credential references,
   cron+timezone next-run maths, prompt builder, run pipeline (topic → generate → image → validate →
   draft/publish → log) with retries, timeouts, dedupe and a per-automation lock.
3. **Scheduler** — `scheduled` handler in a real Worker entry + cron triggers in `wrangler.jsonc`,
   plus a token-protected HTTP tick for external cron/testing. Concurrency 1 per automation, durable
   `next_run_at`.
4. **Automation desk** — management list, per-automation editor, diagnostics (test connection, run
   now, dry run, retry), history with stage/status/duration/next run, draft inspection.
5. **Ticker** — one-at-a-time rotation with a real source list (`trending` = genuine 7-day view
   metric, `recent`, `featured`, `category`, `manual`, `custom` text), interval, count, category
   filter, ordering, live preview, reduced-motion respect, no dead links, never unpublished content.
6. **Homepage builder + sidebar manager** — shared block model, add/edit/reorder/hide/duplicate/
   delete, draft → publish, preview at 3 widths, backward-compatible fallback to today's layout.
7. **Admin dark mode** — Light/Dark/System, persisted, no flash, desk-wide CSS variables.
8. **Admin navigation** — regrouped around the new pages.
9. **Tests + build** — unit tests for all new pure logic, HTTP e2e against local `wrangler dev`
   with local D1/R2, build/typecheck/lint.
10. **Docs** — this document, `docs/ADMIN-GUIDE.md`, `docs/automation/README.md`, README.

## 3. Bugs found while implementing (not in the original audit)

1. **Workerd rejects `redirect: "error"`** — every provider call (`generateArticle`, image generation,
   the connection test) died before leaving the edge with *"Invalid redirect value… use manual"*.
   All three sites now use `redirect: "manual"` plus an explicit `assertNoRedirect()` guard, so a
   provider redirect fails the call instead of forwarding the API key to another host.
   Timeouts were also brought inside Cloudflare's request budget (30 s connection test, 60 s generate,
   60 s image).
2. **A brand-new automation could never run.** `claimRun()` inserted the schedule row *with the lock
   already set*, so the first run reported "already running" and only a lock expiry could clear it.
   The insert now leaves the lock empty and the conditional UPDATE performs the claim.
3. **A stored automation row that fails validation silently turned the automation off** (every field
   fell back to defaults, including `enabled: false`). `parseRecord()` now keeps every field that is
   still valid, resets only the failing ones and logs the problem, so a schema change cannot switch a
   writer off behind the owner's back.
4. **Article sidebar blocks that only know their slug rendered as nothing** —
   `sidebarBlocks()` was called with an empty slug, so the aside came out empty on every article page.
   It now receives the article's id, slug and title.
5. **The scheduler re-ran the plan it had only half-advanced.** `runDueAutomations()` mixed planning
   and acting; it is now a pure planner (`tick-plan.ts`) plus an executor (`scheduler.server.ts`), so
   the slot advance and the run cannot disagree.

- **Homepage builder / Sidebar manager**: block library (hero, article list, topic navigation, tag
  collection, this article's tags, share, text, announcement), per-block settings, drag-free reorder
  with arrows, enable/disable, duplicate, delete, draft → publish → discard, and a preview rendered
  from real published articles.
- **Trending ticker**: label, source, count, interval, rotation, counter, pause-on-hover, free-text
  items, topic filter, hand-picked order (with up/down), and a preview that says when it is falling
  back.
- **Desk theme**: Light/Dark/System in the sidebar, applied before paint.
- **Admin menu** regrouped into Content / Site / Automation / System.
- **Desk error state**: a desk page that cannot load (usually because the database is unreachable)
  renders inside the desk with its own explainer and a Try again link, instead of the public error
  screen (`errorComponent` on the `/admin` route).

## 5. Automation isolation (Phase 3 requirement)

* One row per automation; every field (provider, model, key name, schedule, topic, category, style,
  publishing mode, caps) belongs to that row.
* A run resolves exactly the secret the automation names (`resolveCredential` is an exact-name lookup,
  no cross-provider fallback), so one key can never be spent by a writer that was not given it.
* The desk only ever receives `{ name, configured, fingerprint, length }` for each secret; tests
  assert no `sk-…` value can appear in a response payload or an error message.
* All automation endpoints go through the same guard (`requireAdmin` + `assertSameOrigin` +
  `writesAllowed`), and every write path is refused on read-only deployments.
* MCP stays backward compatible: the connector reads the desk-selected automation and can publish
  only under that automation's policy.

## 6. Ticker behaviour (Phase 4 requirement)

Genuine published articles only. `trending` ranks by real recorded views (see `article_views`),
and while there is not enough readership data it says so and shows the newest articles instead of
inventing a ranking. Disabled or empty → no strip at all (no dangling empty bar). A pinned entry that
is not published, or a topic filter with no matches, falls back with a visible note in the desk
preview. Rotation stops for reduced-motion visitors; links are real article links.

## 7. Database changes (Phase 9 requirement)

`migrations/d1/0004_automations.sql` (applied locally, **additive**):
`automations` (34 columns), `automation_schedule` (per-automation next-run state + run lock),
`automation_runs` (history), `automation_submissions` (idempotency key + content hash + flags),
`article_views` (`article_id`, `day`, `count`). Nothing dropped, nothing renamed; the legacy
`site_settings('automation')` row is still readable. Layout lives in the existing `site_settings`
table as `layout` / `layout:draft` rows, so an existing deployment needs no data migration and the
public site keeps its old layout until a layout is published.
